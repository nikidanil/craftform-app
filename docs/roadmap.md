# Roadmap FormCraft

План разработки FormCraft по этапам. Каждый этап — мержбельный
инкремент. Сначала прокатываем весь happy path (создание формы →
прохождение → просмотр отклика), затем полируем поиск/сортировку/
инфинити-скролл/DnD, в конце добавляем аутентификацию и профиль.

## Подход к разработке

- **TDD по пользовательским сценариям.** Каждая задача внутри этапа
  начинается с теста на конкретный пользовательский сценарий из
  фича-документации: сначала пишется падающий тест (Vitest + RTL),
  потом реализация, доводящая его до зелёного, потом рефакторинг.
  Smoke-тесты в Vitest не пишем — для smoke-проверок и сквозных
  проходов используется Playwright через MCP. К моменту мержа этапа
  критерии завершения подкреплены тестами на сценарии, отдельной
  фазы «допишем тесты» в конце нет.
- **Стек.** React 19 + TS strict, Vite, React Router 7, React Query,
  Zustand, react-hook-form + zod, shadcn/ui, CSS Modules,
  Vitest + RTL, Playwright через MCP. Полный список — в
  `.claude/CLAUDE.md`.
- **Дизайн-макеты.** Для каждой страницы есть HTML-прототип в
  `docs/design/<page-slug>/index.html` (полный список — в
  `.claude/CLAUDE.md`, раздел «Дизайн-макеты»). Перед реализацией
  страницы открываем соответствующий макет и опираемся на него:
  состав компонентов, визуальный стиль, состояния. Позиционирование
  на отдельных макетах слегка неточное — повторять пиксель-в-пиксель
  не нужно, главное — сами компоненты.
- **Подзадачи внутри этапа.** Каждый этап до старта реализации
  разбивается на список подзадач — каждая = один атомарный коммит.
  Список фиксируется в самом этапе (раздел «Подзадачи (коммиты)»).
  Этап с пометкой L обязательно разбивается; M — почти всегда; S —
  обычно одним коммитом. Подзадачи следующих этапов размечаем по
  мере приближения, а не сразу для всего roadmap, чтобы план не
  устаревал.

## Сложность

- **S** — день-два работы, мало незнакомого.
- **M** — несколько дней, есть нетривиальные куски.
- **L** — крупный этап, может разбиваться внутри на подзадачи.

## Этап 1. Каркас приложения

**Что делается.** Поднимаем Vite + React 19 + TS strict, ставим
React Router 7, Zustand, React Query, react-hook-form + zod, shadcn/ui,
Vitest + RTL. Раскладываем FSD-light структуру: `app/`, `pages/`,
`widgets/`, `features/`, `entities/`, `shared/`; заводим barrel-файлы
и алиас `@/`. Настраиваем React Router 7 с заглушками страниц в
`src/pages/` по всем будущим маршрутам, общую шапку оформляем как
виджет в `src/widgets/header/` и рендерим внутри layout без логики
защиты. Поднимаем тестовое окружение (Vitest + RTL + jsdom) так,
чтобы со следующего этапа можно было сразу писать тесты на
пользовательские сценарии в TDD-стиле. Smoke-проход по всем
маршрутам выполняем через Playwright MCP.

**Покрывает.** Частично [`app-shell.md`](./features/app-shell.md)
— состав ссылок и места рендера. Маршруты-заглушки под все остальные
фичи.

**Зависимости.** Нет.

**Критерии завершения.**
- Приложение собирается и запускается (`npm run dev`).
- Линт и тайпчек проходят. Тестовая инфраструктура (Vitest + RTL +
  jsdom) подключена и готова принимать первые сценарные тесты на
  этапе 2; smoke-тестов в Vitest на этом этапе не пишем.
- Маршруты `/`, `/login`, `/signup`, `/me`, `/forms/new`,
  `/forms/:formId/edit`, `/forms/:formId`, `/forms/:formId/responses`,
  `/forms/:formId/responses/:responseId` отдают пустые страницы-заглушки
  через React Router 7; компоненты страниц лежат в `src/pages/`.
- На `protected`-маршрутах (`/`, `/me`, `/forms/new`,
  `/forms/:formId/edit`, `/forms/:formId/responses`,
  `/forms/:formId/responses/:responseId`) виден layout с шапкой —
  виджет из `src/widgets/header/`; на `/login`, `/signup`,
  `/forms/:formId` шапки нет (без логики защиты, просто два варианта
  layout-роута в роутере).
- Smoke-проход через Playwright MCP: все 9 URL открываются,
  ошибок в консоли нет.

**Сложность.** S.

## Этап 2. Мок-API и сущности

**Что делается.** Описываем типы `Form`, `Question`,
`QuestionOption`, `Submission`, `Answer` в `src/entities/*`.
Поднимаем мок-сервер на `json-server` поверх `mocks/db.json`
(in-memory хранилище и seed-данные), проксируем через Vite,
закрываем CRUD по формам и откликам. Делаем базовый React Query
клиент в `src/shared/api`.

**Покрывает.** Никакую UI-фичу напрямую — это фундамент данных
для всех последующих этапов.

**Зависимости.** Этап 1.

**Критерии завершения.**
- Типы сущностей — единый источник правды, импортируются через
  `@/entities/...`.
- Эндпоинты `json-server` (`mocks/db.json`) покрывают: список форм,
  чтение/создание/обновление/удаление формы, чтение публичной формы,
  отправка отклика, список откликов формы, чтение одного отклика.
- В сценарных тестах API мокается точечно по месту (например, `vi.mock`
  на http-клиенте из `src/shared/api/`) — отдельный мок-сервер для
  тестов не поднимаем. Инфраструктура моков подключается с первого
  сценарного теста на этапе 3.

**Сложность.** M.

## Этап 3. Конструктор формы (happy path)

**Что делается.** Реализуем `/forms/new` (создание + редирект на
`/forms/:formId/edit`) и сам конструктор: заголовок, описание,
добавление вопросов трёх типов из бокового меню (клик/добавление,
без drag-reorder), карточка вопроса с телом, вариантами (для списка
выбора), флагом обязательности и кнопкой «Удалить». Кнопки «Сохранить»,
«Удалить форму», «Скопировать ссылку», блок ошибки, сообщение об
успехе. Валидация: заголовок обязателен, минимум один вопрос.

**Покрывает.** [`form-builder.md`](./features/form-builder.md)
(всё кроме DnD-переупорядочивания и удаления вытаскиванием — отложено
на этап 7).

**Зависимости.** Этапы 1, 2.

**Критерии завершения.**
- Можно создать форму, добавить вопросы всех трёх типов, сохранить,
  переоткрыть и увидеть те же данные.
- «Скопировать ссылку» доступна только после первого сохранения.
- «Удалить форму» уводит на `/`.
- Все формы (включая внутренние карточки вопроса) построены через
  `useForm` + `zodResolver`.

**Сложность.** L.

**Подзадачи (коммиты).**
1. `shared/ui`: shadcn-примитивы (button, input, label, select,
   separator, switch, textarea).
2. test infra: общий `renderWithProviders` (`src/test/test-utils.tsx`)
   + правки lint для тестов.
3. `entities/form`: расширение схемы (`choiceVariant`,
   `isChoiceQuestion`).
4. mocks: seed-данные под конструктор форм.
5. `widgets/form-builder`: model — defaults и валидационная схема.
6. `widgets/question-type-panel`: панель типов вопросов.
7. `widgets/question-card`: карточка вопроса с редактором choice.
8. `features/save-form`: сохранение формы (create + edit) + тест.
9. `features/delete-form`: удаление формы и редирект на главную + тест.
10. `features/copy-form-link`: копирование публичной ссылки + тест.
11. `widgets/form-builder`: ui `FormBuilderForm` + barrel + тест.
12. `pages`: подключить `FormBuilderForm` в `/forms/new` и
    `/forms/:id/edit` + тест страницы.

## Этап 4. Прохождение формы

**Что делается.** Публичная страница `/forms/:formId`: тянем форму
по id, рендерим заголовок/описание/вопросы по типам, выделяем
обязательные, валидируем заполнение и отправляем отклик. Экран
успеха заменяет форму.

**Покрывает.** [`form-fill.md`](./features/form-fill.md)
(happy path; обработку сетевых ошибок и повторную отправку — на
этап финальной полировки).

**Зависимости.** Этапы 2, 3.

**Критерии завершения.**
- Форму, созданную в этапе 3, можно открыть по публичной ссылке
  без авторизации.
- Кнопка «Отправить» неактивна, пока не заполнены все обязательные.
- После успеха показывается сообщение об успешной отправке.
- Отклик появляется в моковом хранилище.

**Сложность.** M.

**Подзадачи (коммиты).**
1. `shared/api`: расширить `HttpError` полем `body` (текст ответа
   при `!response.ok`) — нужен для извлечения сообщений API.
2. `widgets/form-fill`: model — defaults и zod-схема ответов
   (динамически по списку вопросов формы).
3. `features/submit-response`: hook `useSubmitResponseAction`
   (обёртка над `useSubmitResponse` с status/errorMessage) + тест.
4. `widgets/form-fill`: ui `FormFillForm` + подкомпонент рендера
   вопроса + экран успеха + barrel + тест.
5. `pages`: подключить `FormFillForm` на `/forms/:formId`,
   обработать загрузку, 404 и сетевую ошибку + тест страницы.

## Этап 5. Главная — список форм (happy path)

**Что делается.** `/` показывает карточки форм текущего «пользователя»
(в прототипе — все формы из мока). На карточке: название, количество
откликов, кнопки «Редактировать», «Посмотреть отклики», «Удалить».
Пустое состояние «У вас пока нет форм. Создайте первую». Без поиска,
сортировки и инфинити-скролла — это этап 8.

**Покрывает.** [`forms-list.md`](./features/forms-list.md)
(базовый рендер и удаление; поиск/сортировка/URL-state/inf-scroll —
этап 8).

**Зависимости.** Этапы 2, 3.

**Критерии завершения.**
- Список форм отображается, кнопки ведут на правильные маршруты.
- «Удалить форму» убирает карточку из списка.
- Пустое состояние видно на чистом моке.

**Сложность.** M.

**Подзадачи (коммиты).**
1. `entities/submission`: hook `useResponsesCountByForm` — один
   `GET /api/responses` с агрегатором `aggregateResponsesByForm` в
   `Record<string, number>` + тест агрегатора.
2. `widgets/forms-list`: model — утилиты `formatCreatedAt` и
   `responsesCountLabel` (русское склонение откликов) + тесты.
3. `features/delete-form`: prop `iconOnly` в `DeleteFormButton`
   (только иконка, `aria-label="Удалить форму"`) + тест.
4. `widgets/forms-list`: ui `FormCard` (карточка одной формы) + тест.
5. `widgets/forms-list`: ui `EmptyState` + `NewFormCard` («+ Создать
   новую форму» в конце сетки) + тест на `EmptyState`.
6. `widgets/forms-list`: ui `FormsList` (корневой грид/пусто) +
   barrel + тест.
7. `pages/forms-list`: подключить `FormsList`, обработать
   loading/error + тест страницы.

## Этап 6. Просмотр откликов (happy path)

**Что делается.** `/forms/:formId/responses` — список карточек
откликов (номер, дата, ссылка «Перейти к отклику»). Сообщение
«Для данной формы нет откликов» при пустом списке. Без сортировки,
фильтров, URL-state и инфинити-скролла — это этап 9.
`/forms/:formId/responses/:responseId` — один отклик, рендер пар
«вопрос → ответ», кнопки «Перейти к форме», «Редактировать форму».

**Покрывает.** [`responses.md`](./features/responses.md)
(базовый рендер; фильтрация/сортировка/inf-scroll — этап 9).

**Зависимости.** Этапы 2, 3, 4.

**Критерии завершения.**
- После прохождения формы из этапа 4 отклик виден в списке и можно
  провалиться в один.
- Read-only страница одного отклика рендерит ответы по типам.
- Навигационные кнопки ведут в нужные места.

**Сложность.** M.

**Подзадачи (коммиты).**
1. `docs`: roadmap — подзадачи этапа 6.
2. `shared/lib`: вынести `responsesCountLabel` из `widgets/forms-list`
   + тесты, обновить импорты.
3. `widgets/responses-list`: model — `formatSubmittedAt` (формат
   `DD.MM.YYYY, HH:MM`) + тест.
4. `widgets/responses-list`: ui `ResponseListItem` (карточка одного
   отклика) + тест.
5. `widgets/responses-list`: ui `ResponsesList` корневой + `EmptyState`
   («Для данной формы нет откликов») + barrel + сценарные тесты.
6. `pages/responses-list`: подключить `ResponsesList` + loading/error/404
   + тест страницы.
7. `widgets/response-view`: model — `findAnswerForQuestion` +
   `getSelectedOptionLabels` + тесты.
8. `widgets/response-view`: ui `AnswerCard` (пара «вопрос → ответ»
   по типам) + тест.
9. `widgets/response-view`: ui `ResponseView` корневой + barrel +
   сценарный тест.
10. `pages/response-view`: подключить `ResponseView` + loading/error/404
    + тест страницы.

## Этап 7. Конструктор: drag-and-drop

**Что делается.** Допилка `form-builder.md`: перетаскивание типа
вопроса из бокового меню в рабочую область, переупорядочивание
вопросов за «6 точек», удаление перетаскиванием за пределы рабочей
области. Подключаем DnD-библиотеку (например, `dnd-kit`).

**Покрывает.** [`form-builder.md`](./features/form-builder.md)
— DnD-часть.

**Зависимости.** Этап 3.

**Критерии завершения.**
- Типы из бокового меню перетаскиваются в форму и становятся вопросами.
- Вопросы переставляются местами захватом за «6 точек».
- Перетаскивание вопроса за пределы рабочей области удаляет его.
- Доступность: DnD имеет fallback (стрелочные клавиши/контекстные
  кнопки).

**Сложность.** M.

**Подзадачи (коммиты).**
1. `docs`: roadmap — подзадачи этапа 7.
2. `chore`: deps — `@dnd-kit/core`, `@dnd-kit/sortable`,
   `@dnd-kit/utilities`.
3. `widgets/form-builder`: model — `useFormBuilderDnd` (sensors +
   `handleDragEnd` поверх pure `interpretDragEnd`) + unit-тест.
4. `widgets/question-card` + `widgets/form-builder`: контекстные
   кнопки «Переместить вверх/вниз» (a11y-fallback), перевод фокуса
   после удаления вопроса + тест.
5. `widgets/question-card`: handle → `<button>`, `useSortable` на
   карточке, transform/opacity при `isDragging`.
6. `widgets/question-type-panel`: `useDraggable` на плитках, клик
   как fallback-добавление сохраняется + тест.
7. `widgets/form-builder`: `DndContext` + `SortableContext` +
   `useDroppable('workspace')` + русские announcements + `DragOverlay` +
   сценарные тесты (add via drag, reorder, drop-outside-delete,
   drop-on-sidebar-NOT-delete, keyboard reorder).

## Этап 8. Главная: поиск, сортировка, URL-state, инфинити-скролл

**Что делается.** Допилка `forms-list.md`: поле поиска по названию,
варианты сортировки (по дате создания, по количеству откликов, по
названию), бесконечный скролл после 30 форм, синхронизация всех
параметров с URL, сообщение «Формы с данным названием не найдены».

**Покрывает.** [`forms-list.md`](./features/forms-list.md)
— оставшаяся часть.

**Зависимости.** Этапы 2, 5.

**Критерии завершения.**
- Открытие страницы по URL с параметрами восстанавливает поиск
  и сортировку.
- При >30 формах докручивается следующая страница, виден индикатор.
- Пустые состояния поиска и общего списка различаются.

**Сложность.** M.

## Этап 9. Отклики: фильтры, сортировка, URL-state, инфинити-скролл

**Что делается.** Допилка `responses.md`: сортировка по дате
(возрастание/убывание), фильтр диапазона дат «от/до», синхронизация
с URL, бесконечный скролл после 30 откликов.

**Покрывает.** [`responses.md`](./features/responses.md)
— оставшаяся часть.

**Зависимости.** Этапы 2, 6.

**Критерии завершения.**
- Открытие по ссылке с параметрами восстанавливает фильтр
  и сортировку.
- При >30 откликах работает инфинити-скролл.
- Пустое состояние отрабатывает и на «нет откликов вообще»,
  и на «фильтр всё отрезал».

**Сложность.** M.

## Этап 10. Аутентификация и защита маршрутов

**Что делается.** `/login` и `/signup` со всеми правилами
(валидация, ошибки «Неверный Email или пароль» / «Введённый Email
уже занят», авто-логин после регистрации). Сессионный store (Zustand).
Защита `protected` маршрутов с редиректом на `/login` и сообщением
«Для просмотра информации о пользователе необходимо войти в систему».
`unauthorized only` маршруты с обратным редиректом и сообщением
«Вы уже вошли в систему». Скрытие шапки на `/login`, `/signup`,
`/forms/:formId`. Кнопка «Выход» в шапке. Привязка форм к автору:
список форм фильтруется по текущему пользователю, чужие формы
для редактирования недоступны.

**Покрывает.** [`auth.md`](./features/auth.md);
полировка [`app-shell.md`](./features/app-shell.md);
ограничение доступа в [`forms-list.md`](./features/forms-list.md)
и [`form-builder.md`](./features/form-builder.md).

**Зависимости.** Все предыдущие этапы (вкручивается «по верху»).

**Критерии завершения.**
- Анонимного посетителя редиректит с любого `protected` маршрута на
  `/login` с нужным сообщением.
- Авторизованного на `/login`/`/signup` редиректит на `/` с нужным
  сообщением.
- После регистрации пользователь сразу авторизован и попадает на `/`.
- Кнопка «Выход» завершает сессию и переводит на `/login`.
- Список форм показывает только формы текущего пользователя.
- Публичная страница `/forms/:formId` остаётся доступна анонимам.

**Сложность.** L.

## Этап 11. Профиль

**Что делается.** `/me` с двумя режимами одной карточки. Просмотр —
поля заблокированы, одна кнопка «Редактировать». Редактирование —
поля разблокированы, «Отменить» (всегда) + «Сохранить» (появляется
при первом изменении, активна только при валидной форме). Обработка
ошибки «Введённый Email уже занят», возврат в режим просмотра при
успехе.

**Покрывает.** [`profile.md`](./features/profile.md).

**Зависимости.** Этап 10.

## Этап 12. Финальная полировка

**Что делается.** Cross-cutting штрихи, которые без них прототип
работает, но не выглядит готовым: toast «Ссылка скопирована» в
конструкторе, человекочитаемая ошибка прохождения формы (сетевая
ошибка / форма удалена) — конкретный текст согласовываем с автором ТЗ
(см. [`form-fill.md`](./features/form-fill.md), раздел «Что не описано
в ТЗ»), а11y-проход по DnD и формам, ревизия покрытия тестами.
Базовое покрытие у нас уже есть из TDD-разработки в этапах 1–11 —
здесь смотрим на дыры и добиваем сквозные интеграционные сценарии.

**Покрывает.** Cross-cutting (все фичи).

**Зависимости.** Все предыдущие этапы.

**Критерии завершения.**
- Сквозные интеграционные тесты на ключевые сценарии: создание
  формы, прохождение, просмотр отклика, логин/регистрация.
- Линт без предупреждений, тайпчек чистый.
- Согласованный текст ошибки прохождения формы зафиксирован.
- А11y-аудит DnD и форм проведён, найденные проблемы закрыты.

**Сложность.** M.

## Релизные рубежи

`dev → main` мержим не после каждого этапа, а на смысловых границах:
там, где сборка `main` представляет собой осмысленную «версию», которую
не стыдно открыть и показать. На каждом рубеже ставим тег по semver
(`v<MAJOR>.<MINOR>.<PATCH>`) — без тега мерж теряет смысл.

| Версия | После этапа | Что в этой версии |
|--------|-------------|-------------------|
| `v0.1.0` | 6 | Полный happy path: создать форму → пройти → увидеть отклик. Без auth, без DnD, без поиска. |
| `v0.2.0` | 9 | Конструктор: DnD. Главная: поиск/сортировка/URL-state/инфинити-скролл. Отклики: фильтры/сортировка/инфинити-скролл. |
| `v0.3.0` | 10 | Аутентификация и защита маршрутов. |
| `v0.3.1` | 11 | Профиль. |
| `v1.0.0` | 12 | Полировка, тесты, a11y. Публичный релиз. |

Между рубежами `main` может временно опережать последний тег
(например, если успел смержить `dev` для бэкапа) — это нормально,
теги ставим только на смысловых границах.

Команды на рубеже:
```
git checkout main
git pull --ff-only
git merge --ff-only dev
git tag -a v0.1.0 -m "v0.1.0 — happy path"
git push
git push origin v0.1.0
```
