# Нефункциональные и технические требования

Здесь зафиксированы требования заказчика из исходного ТЗ, не относящиеся
к конкретной фиче: качества системы, обязательные технологии и
организационные правила. Эти требования объясняют, **что должно быть
обеспечено**.

Конкретный выбор стека и проектные конвенции (какие именно версии
React/TS, какой стейт-менеджер, как именованы CSS-классы и т.д.)
живут в [`CLAUDE.md`](../CLAUDE.md) — этот файл их не дублирует.

## Нефункциональные требования

### Производительность
Приложение должно иметь хорошую производительность и быстрый отклик.
Конкретных метрик в ТЗ нет — целимся в субъективную «не лагает»:
интерактивные элементы откликаются мгновенно, переходы между
страницами не блокируют интерфейс.

### Поддерживаемость и масштабируемость
Архитектура должна позволять без болезненных переписываний:
- добавлять новые типы вопросов,
- добавлять новые страницы и роуты,
- расширять модель отклика.

### Адаптивность (желательно)
Приложение должно корректно отображаться на устройствах разных
размеров — настольные компьютеры, планшеты, телефоны. Помечено
в ТЗ как «желательно», т.е. не блокер релиза, но цель.

## Технические требования

### Язык и фреймворк
- Код пишется на **TypeScript**.
- UI реализуется на **React**.

### Управление состоянием
В приложении должен использоваться менеджер состояния. Конкретный
выбор библиотеки — в `CLAUDE.md`.

### Тестирование
- Тесты пишутся на **Vitest** + **Testing Library**.
- Покрытие тестами — по максимуму.
- Рекомендуется вести разработку через тестирование (TDD).

## Пояснения и допущения из ТЗ

Эти пункты в ТЗ оформлены как «пояснения» — они задают рамки
выбора инструментов, но оставляют свободу.

### Сборщик
Любой по выбору команды — например, Webpack или Vite. Конкретный
выбор фиксируется в `CLAUDE.md`.

### Стилизация
Допустимые подходы:
- **CSS Modules**,
- библиотеки компонентов **shadcn/ui** (Tailwind применяется только
  внутри самих shadcn-компонентов).

### Серверная логика
Может быть **замокана** — например, через Postman Mock Server,
программу-сервер или другой инструмент/сервис. Реальный backend
для сдачи ТЗ не требуется.

### Версионирование и git
- Работа ведётся через **Git** по выбранной методологии (например,
  Git Flow).
- Версии релизов нумеруются по [семантическому версионированию](https://semver.org/).
